TECHNICAL PILLARS

What the design must get right.

The goal is not a single clever lock. It is a set of explicit security invariants across processes and failure states.

01 / IDENTITY

Verified volume binding

Local fixed NTFS scope, stable volume identity and root file identity, checked where authority is exercised.

Native foundation under development
02 / OWNERSHIP

Single authority per volume

Competing brokers must not simultaneously grant filesystem authority. A scratch prototype demonstrates cooperative exclusion.

Simulated prototype evidence
03 / LIFECYCLE

Atomic admission and drain

New work stops at drain; registered in-flight operations finish before normal ownership release.

Simulated prototype evidence
04 / GENERATIONS

Stale authority rejection

Generation binding limits future admissions. The harder question—already-issued kernel I/O and late effects—remains open.

Real native I/O proof pending
05 / RECOVERY

Fail closed after uncertainty

Unexpected termination enters recovery-required state. Automatic restart does not itself authorize recovery.

Real crash guarantee pending
06 / ISOLATION

Windows-enforced boundary

Dedicated service identity, narrowly scoped pipe ACLs, token verification and protected state are proposed, not yet exercised.

Service implementation not run
WHY A BROKER?

Cross-process security is a systems problem.

Traditional per-process locks and state can fail to describe an entire process's in-flight work or safely coordinate recovery after a crash.

The proposed broker makes one subsystem responsible for admitting operations, maintaining an operation registry, and deciding whether the system can safely return to service.

Read the experiment results
FIVE PROBLEM GROUPS
  1. Conflicting authority across processes
  2. Lock ownership and race conditions
  3. In-flight work and orderly shutdown
  4. Stale generations and late writes
  5. Crash uncertainty and human-authorized recovery

Prototype results support the first three at simulation level. The remaining guarantees require OS-level evidence.

Security boundary disclosure. Module privacy, service process separation, and a successful simulation are not security certifications. AegisFS V1.0 is Windows-local/fixed-NTFS focused; network and removable storage are outside its initial scope.
